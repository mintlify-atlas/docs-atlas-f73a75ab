Social Media Backend uses [pydantic-settings](https://docs.pydantic.dev/latest/concepts/pydantic_settings/) to load all runtime configuration from environment variables or a `.env` file placed in the project root (the directory containing `pyproject.toml`). Every variable listed below is **required** — the application calls `Settings()` at import time and will raise a `ValidationError` and refuse to start if any variable is absent or incorrectly typed.

## Environment file template

Copy the block below into a file named `.env` in the project root and fill in your values before starting the server.

```bash .env
DATABASE_HOSTNAME=localhost
DATABASE_PORT=5432
DATABASE_PASSWORD=your_password
DATABASE_USERNAME=postgres
DATABASE_NAME=social_media
SECRET_KEY=your_super_secret_key_here
ALGORITHM=HS256
ACCESS_TOKEN_EXPIRE_MINUTES=60
```

<Warning>
  **Never commit `.env` to source control.** The file contains your database credentials and JWT signing secret. Add `.env` to your `.gitignore` immediately.

  ```bash
  echo ".env" >> .gitignore
  ```
</Warning>

## Variable reference

### Database connection

The application constructs the SQLAlchemy connection URL internally as:

```
postgresql://{DATABASE_USERNAME}:{DATABASE_PASSWORD}@{DATABASE_HOSTNAME}:{DATABASE_PORT}/{DATABASE_NAME}
```

<Note>
  You do **not** set a `DATABASE_URL` variable directly when running locally. The URL is assembled automatically from the five individual database variables below. (On Render, `DATABASE_URL` is injected as a platform variable and takes a different code path — this only applies to the hosted deployment.)
</Note>

<ParamField env="DATABASE_HOSTNAME" type="string" required>
  Hostname or IP address of the PostgreSQL server. Use `localhost` for a local instance or the hostname provided by your managed database service (e.g. Render, Supabase, or AWS RDS).

  **Example:** `localhost`
</ParamField>

<ParamField env="DATABASE_PORT" type="string" required>
  TCP port on which PostgreSQL is listening. The default PostgreSQL port is `5432`. Change this only if your PostgreSQL instance is configured to listen on a non-standard port.

  **Example:** `5432`
</ParamField>

<ParamField env="DATABASE_USERNAME" type="string" required>
  PostgreSQL role (username) the application connects as. The role must have `CREATE`, `SELECT`, `INSERT`, `UPDATE`, and `DELETE` privileges on the target database, plus permission to run Alembic migrations.

  **Example:** `postgres`
</ParamField>

<ParamField env="DATABASE_PASSWORD" type="string" required>
  Password for the PostgreSQL role specified in `DATABASE_USERNAME`. This value is included verbatim in the connection URL, so avoid characters that require URL encoding (e.g. `@`, `#`, `/`) unless you handle encoding separately.

  **Example:** `my_secure_db_password`
</ParamField>

<ParamField env="DATABASE_NAME" type="string" required>
  Name of the PostgreSQL database the application connects to. The database must already exist before you run `alembic upgrade head`. Create it with:

  ```bash
  createdb -U postgres social_media
  ```

  **Example:** `social_media`
</ParamField>

### JWT authentication

<ParamField env="SECRET_KEY" type="string" required>
  Secret used to sign and verify JWT access tokens. This value must be long, random, and kept private. Anyone who knows this key can forge valid tokens for any user in the system.

  Generate a secure value with:

  ```bash
  openssl rand -hex 32
  ```

  <Tip>
    A 64-character hex string (32 bytes of entropy) produced by `openssl rand -hex 32` is the minimum recommended length. Do not reuse this value across environments.
  </Tip>

  **Example:** `a3f8c2e1d4b7a09e6f2c5d8b1e4a7f0c3d6b9e2f5a8c1d4b7e0f3a6c9d2b5e8`
</ParamField>

<ParamField env="ALGORITHM" type="string" required>
  The signing algorithm passed to PyJWT when creating and decoding tokens. The application currently uses HMAC-SHA256. This value must match on both the signing and verification sides, so only change it if you also update `oauth2.py` accordingly.

  **Supported value:** `HS256`

  **Example:** `HS256`
</ParamField>

<ParamField env="ACCESS_TOKEN_EXPIRE_MINUTES" type="integer" required>
  Lifetime of an issued JWT access token, expressed in whole minutes. After this period the token is rejected with a `401 Unauthorized` response and the client must log in again to obtain a new token.

  Choose a value that balances security with user experience — shorter lifetimes reduce the window of exposure for a stolen token, while longer lifetimes reduce how often users must re-authenticate.

  **Example:** `60` (tokens valid for one hour)
</ParamField>

## How settings are loaded

The `Settings` class in `app/config.py` inherits from `pydantic_settings.BaseSettings`. At startup, pydantic-settings reads variables from the process environment first, then falls back to the `.env` file declared in the inner `Config` class:

```python
from pydantic_settings import BaseSettings

class Settings(BaseSettings):
    database_hostname: str
    database_port: str
    database_password: str
    database_username: str
    database_name: str
    secret_key: str
    algorithm: str
    access_token_expire_minutes: int

    class Config:
        env_file = ".env"

settings = Settings()
```

The module-level `settings` singleton is imported throughout the application (e.g. in `database.py` and `oauth2.py`), so it is evaluated once at import time. Any missing or mis-typed variable causes an immediate startup failure with a descriptive validation error.

<Tip>
  In production (e.g. Render, Railway, Fly.io), set these variables as platform-level environment variables rather than deploying a `.env` file. Process environment variables always take precedence over the `.env` file, so the same `Settings` class works in both local and deployed environments without any code changes.
</Tip>
